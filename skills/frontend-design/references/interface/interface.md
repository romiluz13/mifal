# Interface design

Support the current Matt phase. Engineering Workflow owns progression; Team
Lead selects procedures and accepts evidence. A solo agent does both in its
existing plan.

## Select the work

| Request | Read before doing its work |
|---|---|
| New interface, redesign, journey or interaction changes | [Design and UX](design.md) |
| Behavior-only form, navigation, loading, error or recovery repair | [Design and UX](design.md), only affected UX sections; preserve the established visual direction |
| Purposeful animation, motion identity or interaction timing | [Motion craft](motion.md), then the actual runtime's version-matched docs |
| Procedural illustration, interactive drawn art, 3D scene or rendered film | [Creative engines](engines.md), only the matching branch |
| Accepting changed user-visible behavior | [UX acceptance](../../../team-lead/references/ux-acceptance.md) and the checks selected in the existing plan |

A behavior-only form repair reads the applicable UX guidance without inventing
a visual redesign. Backend changes enter this branch when they change a user
journey. Backend work without that effect keeps its normal engineering checks.

## Before building

Read the existing product requirements, design system, task state and rendered
interface. Identify the person, primary task, meaningful states and constraints.
Reuse facts and settled decisions. Ask only for consequential missing intent;
keep assumptions visible in the existing plan. This specialist introduces no
new interview, tracker, context document or authorization stage.

Choose one interface direction. For an unresolved high-value visual or
interaction decision, use Matt's prototype detour and compare small working
alternatives within a named budget. A clear brief proceeds directly.

For interactive/web output, check the selected worker's browser tools before
promising visual or interaction checks. Inspect the existing route when it is
available; inspect a new route once built. Before acceptance, capture and
inspect its rendered state, actuate relevant controls and read errors through
available permitted tools. A skill file, screenshot intention or successful
build is insufficient. Use a capable existing reviewer when available; an
unavailable required check stays untested.

For rendered video or static art without an interactive surface, select
artifact-appropriate evidence instead: inspect the actual rendered artifact,
representative frames and composition; verify duration, timing and audio when
applicable to the brief. Website controls and viewport checks are required only
when the task also delivers an interactive/web surface.

## Build, review and hand back

Use the project's existing components and libraries. Keep content and controls
usable while assets load, when motion is reduced and when decorative code
fails. Implement inside Matt's selected build/debug procedure.

Compare the rendered result with the brief and exercise the affected journey
for interactive output. Use one batched relevant inspection (desktop/mobile
for web surfaces; selected frames/timing/audio for rendered media), fix its
findings, then one confirmation pass; expand only for an unresolved concrete
defect. Correctness gates remain required; reaching a polish cap with an open
gate means a hold.

Return the loaded reference paths, selected runtime, observed behavior and
evidence at the final revision through the existing task receipt. Distinguish
visual screenshots, interaction checks and real-user validation. Team Lead
checks an omitted applicable specialist and its evidence before acceptance.
