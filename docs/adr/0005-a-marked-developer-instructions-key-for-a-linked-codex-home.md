# A named Codex Home whose rules file is a link gets the Guide as one marked key in its own config.toml

Some developers link a Codex Home's `AGENTS.md` to one shared rules file, which ADR 0004 refuses to write through. For a Codex Home named with `--home` whose `AGENTS.md` is such a link, Mifal writes one Mifal-marked top-level `developer_instructions` key holding the Guide at the top of that Home's own `config.toml`, before any table. The link stays a link, the shared file is never written, and ADR 0004 stands for every other linked rules file, including a linked Codex Home nobody named.

Mifal owns only the marked block's bytes. It parses the whole original and the whole result with a vendored `tomli` 2.4.1 and writes nothing when the key already exists in any form (top level, quoted, dotted, or inside any table, profile or array of tables), when `config.toml` is a link or not UTF-8 TOML, when it holds a Mifal marker this install did not write, or when the result would not read back as the original plus exactly the Guide. Every other byte keeps its place, line endings included. An owner-only (0600) copy of an existing file is recorded first. Update refreshes, and uninstall removes, only a block whose bytes match the record; an edited, moved or duplicated block holds the whole plan and keeps its backup. Preview, doctor and failures name the path and the key, never a value. Doctor claims the block's integrity, not that a session loaded it.

The read exception to ADR 0003: Mifal reads the served Codex Home's own regular `hooks.json` and the `[hooks]` table of its `config.toml`, as data in the shape Codex 0.164 reads, only to avoid a second copy of the Guide. A `SessionStart` command that names the installed Guide, or any `SessionStart` handler Mifal cannot classify, makes the Home pending: it is recorded without a key, named apart from the wired Homes, and checked again on every install, update and doctor run. A linked, unreadable or unsupported hook file is unknown and gets no key either. A hook that appears beside an owned key holds the plan. Mifal never runs, follows, edits, backs up or prints a hook, and never delivers the Guide through one; ADR 0003's ban on hook edits and hook delivery stands.

Rejected: replacing the link with a generated file (B1), which changes a file the developer chose to share, and writing into the shared file (B2), which wires Homes nobody named.

Consequence: the key is a replaceable scalar. A selected profile file, a `-c developer_instructions` flag or a trusted project's `.codex/config.toml` replaces it for that session (Codex 0.164.0, initial request only), and Mifal cannot see those. Codex 0.164 reads hooks from both `hooks.json` and an inline `[hooks]` table in `config.toml` (`config_toml.rs`, `hook_config.rs`), and the official hooks page says Codex merges them; the retained source lacks the loader, so Mifal treats both as active, the conservative reading. It classifies a `SessionStart` handler in either with the same rules, ignores the table's `state` trust records, and records a hook file or table it cannot read as unknown, not pending, with no key.
